# P6.4 preference memory evidence (2026-09-24)

## Scope and behavior

Original P6.4 is implemented without adding, splitting or dropping roadmap items. The workbench opens `MemoryActivity` for scoped browsing, value editing, deletion and JSON import/export. Each entry has `key`, `value`, `scope`, `sourceRunId`, `createdAt` and `updatedAt`. Keys and scopes remain stable while editing values. Source task IDs and timestamps are visible. The retained collection is bounded to 500 entries / 256 KiB, with at most 4096 Unicode code points per value.

`memory_get` and `memory_propose` use the existing catalog and public Agent decision contract. No new JavaScript methods, public AIDL transactions, runtime dependencies or permissions are introduced. The model and device brokers remain host-owned. Proposals are read-only during preparation and carry the effective scope into confirmation, including the default `global`. The full bounded value is shown even when its escaped JSON exceeds the ordinary 4 KiB argument summary.

Every proposal requires an individual confirmation. Task-wide permission cannot bypass it. Denial returns `USER_DENIED` to the model without a write. The stored source ID is supplied by the actual runner, not by the model. If the same entry changes between preparation and confirmation, the write fails instead of replacing the newer value; another proposal and approval are required. Cancellation before a queued mutation starts prevents that mutation. An already completed atomic write is not rolled back by a later task cancellation.

Reads and writes are restricted to the current preset's permitted subset of global and current-preset scopes. No other preset can be addressed by `memory_get` or `memory_propose`. Prompt data exposes the allowed scope names. Global is the catalog's default proposal scope, so a preset-only task must specify its own preset name. A preset with no memory scope rejects both tools.

The existing `memory: false` option still controls automatic injection only. To also disable explicit reads and proposals, disable the memory tool group or use a preset with no memory scope. Injection keeps whole entries, newest first, within 4 KiB. A current-preset value wins an exact-key collision with a global value. Overflow is explicit; a first oversized entry is not partially inserted. `memory_get(keys)` can retrieve an older selected value omitted from initial injection, with a bounded reply and explicit truncation. The initial task snapshot is fixed; later tasks see newly confirmed preferences. The first task after process startup waits asynchronously for storage initialization instead of treating an unfinished load as an empty store.

## Persistence and private management

`MemoryRepository` is the sole owner in `:agent`. It serializes storage operations on a bounded worker queue. Binder calls do not perform disk IO. `MemoryStore` writes a separate versioned file under `files/memories` for each scope/key identity; names are SHA-256 hashes of the JSON identity pair. A mutation writes only that entry. Synced temporary contents and a backup protect replacement, and publication follows a successful write. Updates to other entries are not rewritten. The 256 KiB retained limit counts serialized entry files; temporary/backup files need additional working space. Exported JSON is also capped at 256 KiB.

Validated backups recover interrupted writes. Legacy version-1 `agent-memory.json` snapshots are migrated, with already migrated entries taking precedence if a previous migration stopped partway. The old snapshot is removed only after the new collection is validated and written. Unknown versions, malformed UTF-8, mismatched file identities and invalid rows fail closed and preserve the source. The old standalone read-only adapter has been replaced by repository integration and corresponding Android migration tests.

The unexported `AgentLocalService` exposes a same-UID asynchronous `IMemoryStore` endpoint. Requests are bounded to two serialized rows plus envelope overhead. Responses above 32 KiB use an unlinked, read-only file descriptor. There is no bulk-write import operation. UI saves and deletes use the reviewed prior row as a conflict check.

Import uses the system document picker without storage permission. The whole JSON file is validated before review, then each row requires its own confirmation. Existing values are shown before replacement. Skip and cancel do not save the remaining rows. A missing preset scope cannot be imported until that preset exists. Restoring a pending import or an unsaved edit never grants permission to write. Import provenance is backup metadata, not authorization.

Export uses the system save picker and includes actual preference values and source metadata, as a usable backup. The UI explains this before choosing a destination. Unlike the history diagnostic export, it is not redacted. Credential-related keys and recognizable bearer/API-key/private-key/token forms are rejected during proposal, import and editing. This is validation of recognizable forms, not a claim to identify every secret disguised as ordinary text. Users must not store credentials in preference memory.
